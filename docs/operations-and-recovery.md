# Operations and recovery

## Ownership and observability

Assign an organization owner for database/Auth/SMTP access, a frontend deployment owner and an incident contact before release. Monitor hosted frontend availability, a real authenticated workspace read, Auth failures/rate limits, Edge Function errors and Supabase database health/advisors. A static homepage alone is not a database health check.

Sentry is optional in local development and requires the environment's public DSN for hosted monitoring. Data collection excludes user data, cookies, headers, bodies, query parameters, database values and local stack variables. Error-event scrubbing removes request/user/context/breadcrumb/extra details and replaces exception messages while retaining code locations. No replay/performance tracing is enabled. Test a controlled staging error and verify actual receipt before calling monitoring operational. Alerting/delivery must be monitored separately.

Application audit/history is generated by the database with authenticated actor IDs and server timestamps. Users cannot directly insert/update/delete it. No authoritative browser-data fallback exists. The frontend differentiates failed writes from writes committed before a refresh failure; inspect/refetch before retrying such an operation.

## Backups and restoration

Choose backup retention, recovery-point and recovery-time objectives with the organization owner and verify the selected Supabase plan's backup/PITR capabilities and costs. Do not assume a plan includes restoration or file backups. There are currently no application upload buckets. If uploads are added, object backup/restoration needs its own procedure.

Before migrations, verify the last usable backup, export migration history and record the frontend release commit. Restrict database exports: they contain employee and organizational data. Keep them in an encrypted access-controlled store rather than Git or public hosting artifacts.

Restoration drill (not yet executed): create a separate isolated recovery project, restore the selected backup using Supabase's supported restore workflow, compare row counts and integrity constraints, verify migrations/functions/grants/RLS, confirm owner/admin access and two-user workflows, and record elapsed recovery time and loss window. Restore Auth identities consistently with membership user IDs; ordinary table exports alone do not constitute an Auth-system backup. Point a private frontend preview at recovery and verify it before any traffic switch. Do not replace the active project during a drill.

## Rollback and migration recovery

Frontend: redeploy the last verified compatible release with the same environment configuration, verify sign-in and workspace reads, then observe errors. Preserve database data. A rollback to the original demo release is not a safe production rollback because it has no real authentication/persistence.

Database: use forward repair migrations when possible. Initial migrations are additive for a dedicated project; do not reverse them by dropping application tables or Auth triggers with live users. For failed migrations inspect transaction/migration history before retrying. If a restore is necessary, verify a separate recovered project and its Auth data before changing frontend configuration. Record approval, backup reference, affected rows and recovery verification. Use backward-compatible schema changes to keep old/new frontend versions functioning during deployment.

## Incident troubleshooting

- Login fails: check environment matches intended project, Auth status, signup/invitation settings, mail limits and redirects. Never change membership roles to bypass an Auth issue.
- Workspace read fails: verify active membership, project membership, assignment and schema grants/RLS. Do not disable RLS to fix permissions.
- Stale-update rejection: refetch, inspect the other change and retry deliberately. Never overwrite the version field from the browser.
- Account frozen/inactive: database access is denied immediately even with an old JWT. End/revoke refresh sessions through owner-controlled Auth administration; access-token expiry alone is insufficient. React rechecks membership on focus and every minute.
- Invitation/recovery request fails: verify APP_ORIGIN, function deployment, server variables, scoped administrator access, the per-employee 60-second request limit and SMTP/provider status. Audit records say requested, not delivered.
- Email changed: confirmed Auth email synchronizes membership email; uniqueness conflicts require owner review rather than merging identities automatically.
- Potential data exposure: preserve audit evidence, revoke affected sessions, correct the scoped authorization rule, run positive/negative direct API checks and restore access only after validation. Do not rewrite audit events.

Hosted monitoring, real backups, a restoration drill and rollback drill remain release blockers. Docker CLI is present locally, but the Docker daemon was unavailable; isolated SQL tests used PGlite, not the full Supabase runtime.
